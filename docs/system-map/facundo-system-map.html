Facundo · architecture at a glance

Facundo System Map

Two products share one repo. Discovery & Recruiting finds and signs florist shops. Production takes a real Shopify order, places it with a florist, pays the split against a delivered photo and writes the result back to Shopify. The order loop below is generated from dashboard/lib/lifecycle.ts, the same file that renders /lifecycle.

Layer 3 · the decision

How one shop is chosen

This is the Match stage drawn out. It runs in match.ts, one shared file that both the worker and the dashboard use.

NO AI

No AI model picks the shop. The choice is a fixed rule that anyone can recompute. The same order and the same shops always give the same ranking, and each candidate is saved with the score breakdown that put it there. Every number below is a setting in Settings → Matching. If a setting is missing or broken, that one value falls back to its default, so a bad row can never stop matching.

1

Find shops near the address

Look inside a box around the delivery point, as wide as the 20 km cap, across every city.

2

Drop who can't take it

  • Test shops
  • Denylisted or lost
  • No trust tier, so we can't pay them
  • Below the rating floor (off by default)
  • Distance unknown, or past their radius
  • Already full for that day
3

Sort by distance ring

0–5 km, then 5–10 km, then 10–20 km. A shop in a nearer ring always ranks above one further out, whatever their scores.

4

Score inside each ring

Inside a ring, a weighted score decides the order. The weights are in the table below.

5

Keep the top 3

Merge duplicate listings of one shop and shops sharing one inbox. Save the best 3 as ranked candidates for the order.

Example: three shops around one delivery

C is past the cap and is dropped in step 2. A shop that says it covers 50 km is still held to 20 km. A shop that gives no radius is treated as covering the full 20 km.

A shop that never joined is offered automatically only when all of these pass. Otherwise the offer waits for approval.

Automation modes

manual A person sends each offer. Waves only keep offers fresh and escalate.
semi The system proposes match, offer, reassign, customer emails and write-back. A person approves each.
auto The wave engine runs unattended, up to the wave limit, stopping a reserve window before delivery.

Money

The trust tier sets the split, 70/30 by default or paid in full. The total floors to a whole euro. The accept leg pays on acceptance and the delivery leg on the photo, in every mode.

Layer 6 · AI architecture

Inside each AI step

Each AI step has the same shape. None of them is an open-ended agent with tools. Code collects everything first, the model fills in one fixed form, and a fixed rule decides what to do with the answer.

1TriggerA scrape, an inbound message, an upload
2Code collects the contextCrawler, regex, database facts, help articles. This is the only "tool use"
3One model callVia OpenRouter. The model must answer by filling one fixed form
4A fixed rule decidesThresholds, escalation lists, consensus
5Safe fallbackKeep, leave empty, send the template or hand to a person

Every call goes through openrouter.ts or a sibling: 30 second timeout, up to 3 attempts on rate limits and server errors. A credit or key outage stops the whole run instead of spoiling rows.

How does the model know it's a florist?

Florist relevance check

Mostly it doesn't need to. Free rules decide most places. The model judges only unclear ones, from the Google Maps listing alone.

InputA place from Google Maps (Apify): name, address, categories, rating, review count.
Free rules first
  1. A shop a person already acted on is always kept.
  2. No Maps category at all: dropped. These are usually village names.
  3. Category contains a local florist keyword: kept, unless a disqualifier appears (dried, wholesale, CBD, artificial, funeral).
The keywords come from a per-country table. Its first fill was one model call. After that it costs nothing.
Model callSonnet 5. Sees the listing fields only, never the website. Told that a "no" is permanent, so prefer "yes" when unsure.is_florist · confidence · reasoning
DecisionOnly is_florist counts. Confidence is logged but not used. A "no" means the place is never saved.
FallbackAn error or a malformed answer keeps the place. If too many calls fail, the run stops.
Problems seen in production
  • Twelve cannabis shops passed the free rule with no model call. That is why disqualifiers now exist.
  • A funeral home got the free pass and received a real order offer.
  • One run saved 610 places, including 80 lottery kiosks and a royal palace garden.
What tools does it use to pick the phone, email and owner?

Contact enrichment

The tools are code, not the model. A crawler and pattern extractors find candidates. The model only picks the real one from that list.

CrawlHomepage plus up to 7 pages on the same site, ranked by URL: contact, legal notice, about, shop, team. 15 s and 1.5 MB per page. Plain fetch only, because the headless browser is switched off in production.
Extract without AI
  • Email: text, mailto:, hidden-email decoding, schema.org, "name (at) domain" text. Junk domains and noreply are dropped.
  • Phone: tel:, schema.org, WhatsApp links, then a pattern match.
  • ±180 characters of text around each candidate.
The Google Maps phone is stored separately and never shown to the model.
Model calls
  • Email: Haiku 4.5 picks the shop's own address or null.
  • Phone: Haiku 4.5 picks the main number or null.
  • Owner: Sonnet 5 reads about, contact and legal text (up to 8,000 characters) and returns owner name, one shop detail and the page language.
  • Online shop? Sonnet 5, only when no rule signal settles it.
DecisionThe pick is stored as returned. The prompts say "null rather than guess". Confidence is not used for email or phone.
FallbackA failed call leaves the field empty and writes why in the enrichment notes. 90 s limit per shop. A repair mode re-runs spoiled rows.
Problems seen in production
  • A credit outage wrote a billing error onto 1,065 shops before the run stopped.
  • The crawl spent its 8 pages on cart pages and missed the address page.
  • 122 out of 1,000 shops with no email had no about or contact page the crawler could find.
  • Shared head-office emails sent one order's offer to one inbox four times. Matching now merges shared inboxes.
  • CLAUDE.md says owner extraction runs on Haiku. The live worker uses Sonnet, so the docs are out of date here.
What problems does the LLM face when it personalises the email?

Recruiting email personalisation

The model never writes the pitch. It rewrites an approved email in the shop's language, adds the owner's name and an opener from research, and must keep everything else.

TriggerStaff pick up to 25 shops on /discovery and ask for drafts. 5 run at a time.
ContextThe approved catalog email, rendered first. Shop name, rating, reviews, city. The owner name and shop detail found at enrichment. The language from Google Maps for that country.
Model callSonnet 5, because cheaper models sound stilted to a stranger in another language. Rules: keep the 70/30 split and the join link, invent nothing, no placeholders, greet by name only if known, add an English copy below.Subject: … then the body
CheckThe reply must start with Subject: or it is thrown away. Long dashes are removed afterwards.
FallbackAny failure sends the approved template unchanged. Staff see the draft before sending.
What makes it hard
  • Language. The target is the country's language, not the site's. Swiss and Austrian shops got English when their country was taken from the ingest city.
  • Two languages can disagree. This route does not use the newer locale resolver. A shop with no saved locale gets an English brief and a local target language.
  • Invented facts. Made-up owner names or "I read your reviews" when nobody did. The prompt forbids both, but no code checks for them.
  • Format drift. On the first live run the model put five long dashes back in. Without the Subject line, sending falls back to a generic subject.
  • Unchecked terms. Nothing verifies that the 70/30 split, the link or the length survived the rewrite.
How are the draft replies generated?

Reply agent

Each inbound message gets one engine run, whatever channel it came in on. The model drafts. A separate fixed guard decides whether the draft is sent.

Comes inEmail reply, SMS reply or in-app message
Before any AIDrop duplicate events. Find the florist by email or phone, the order by reply token. Opt-out words close the thread. Auto-replies are stored, not answered. Unknown senders go to a person.
Context, all loaded up frontUp to 10 messages of the thread, the persona for the florist's language. Support: this order's facts (payout, photo verdict, address, recipient) and 11 published help answers. Recruiting: the pitch and 7 approved facts.
One model callSonnet 5 (a setting). Fills one form:intent · reply_text · language · confidence · escalate · facts_asserted
The guardThe draft goes to a person if any of these fire:
  1. An open issue on the order
  2. An intent that always escalates: complaint, opt-out, wants a person, order change, delivery problem, terms, pricing, legal, unclear
  3. Asked "are you a bot?" and the reply doesn't admit it
  4. 3 automatic replies already sent
  5. The model flags it itself
  6. Confidence below 0.75
  7. A money amount not in the allowed facts, or a promise phrase
Goes outSent as the persona by email (Resend), SMS (Telnyx) or in the app. The first reply says it is automated. If held, it is saved as a draft and the thread lands on the CX desk.
Recruiting intents (10)interested, logistics, pricing, legal, complaint, opt-out, wants a person, asked if AI, not now, unclear
Support intents (13)order status, payout status, photo help, how it works, app how-to, delivery problem, change request, terms, complaint, opt-out, wants a person, asked if AI, unclear
Known gaps
  • Reads the oldest 10 messages, not the latest (agentTurn.ts:147). A long thread loses its recent context.
  • Escalated threads still get AI replies. Nothing in the turn checks whether the thread is already waiting for a human, so a new message can be auto-answered if it passes the guard.
  • Facts are read once at the start of the turn. If the order changes mid-turn, the reply can be stale. Marked open in the lifecycle map.
  • The specs name the main risk: a wrong intent label is the whole risk surface, because the guard trusts the label.
How does it answer florist questions as a chat?

In-app support chat

Same engine as the reply agent, opened from a chat box on the order page. App and email share one thread.

Example turn, illustrative wording
Florist: when do I get the rest of the payment?
The app checks the order belongs to this florist, finds or opens the support thread, saves the question (max 4,000 characters), then runs the reply engine.
The model sorts the question as payout_status. It answers from this order's payout facts and the published help: the delivery leg is released when the photo is uploaded.
The guard passes it. The intent is safe, the confidence is high and every amount is in the allowed facts.
Assistant (automated): you'll receive the remaining 30% as soon as your delivery photo is uploaded…
If the guard holds it, the florist sees nothing automatic. CX picks up the thread on the desk, replies, and the assistant takes over again with the reply count reset to zero.
Worth knowing
  • The chat appears only after the florist has accepted the order, and only when the florist chat setting is on.
  • The in-app path skips the opt-out keyword check that email and SMS have. Only the guard's opt-out intent catches it.
  • The florist never sees held drafts. Only sent and received messages show.
What does it use to get the delivery photo right?

Delivery photo check

A guide on screen before upload, a file check, then two vision models that compare the photo with the order's text. Today the result is recorded only.

Before uploadFive rules above the button: everything in one frame, good light, plain background, sharp, taken at this delivery. Four sample tiles: one good, three bad (dark, blurry, cut off). No camera-only capture, so the photo library works too.
UploadMax 8 MB. The real file bytes must be JPEG, PNG or WebP; HEIC is refused. Stored in R2. The order is marked delivered straight away. EXIF data is not read.
Two models voteClaude Sonnet 5 and Gemini 2.5 Flash run in parallel. Each gets the photo plus a text list of the order, such as "2× Title (variant) [type] — recipe". Asked to be strict about blurry, generic, stock or partial photos.matched · confidence · items found · items missing · notesTwo more models run in shadow mode with product reference photos. They never count.
Consensus
  • A vote is review if confidence is under 0.7 or anything is missing
  • Both pass → pass
  • Both fail → fail
  • Any review, or pass versus fail → review
  • One model down → the other decides alone
  • Neither answered → review
What it drivesNothing about money since 2026-08-20. The delivery payout releases on upload. Staff see a QA-only panel, and the support assistant can quote the verdict.
Why it doesn't gate payouts
  • An audit of every early verdict found 5 out of 5 marked review, none pass or fail. Two were photos of shoe boxes on a couch that it still did not fail.
  • The voting models don't see the product photos, the recipe components or the add-on list. Only the shadow models get reference images.
  • No check for recycled or stock photos beyond the prompt, and no time or place check. Both are marked open in the lifecycle map.
  • The two voting calls have no timeout, and the upload waits for them.
  • Two code comments still say the verdict holds the payout. They have been wrong since 2026-08-20.
